# Cadenza project specification

Version 0.4, 26 October 2026. Intended implementers are the developers of Cadenza Host and Cadenza Remote. This baseline is extended by the latest [Cadenza implementation goalset](docs/agents/GOALSET.md). [Validation](docs/agents/VALIDATION.md) records exact verified revisions and remaining checks. Host compilation and target-device integration remain pending. Partial local checks do not establish application conformance.

## Scope and terminology

**Cadenza** is the overall project. **Cadenza Host** is the macOS companion controlling the existing Music.app. **Cadenza Remote** is the native Android interface. One Host serves multiple simultaneously paired Remotes on a local network. Audio remains in Music.app on the Host computer.

The Host runs on a supported Apple silicon Mac with macOS 26 or newer. The Remote runs on a supported Android device with Android 12 / API 31 or newer. English is the initial translation target. Personal use without paid Apple Developer membership is a mandatory constraint.

A **request** is one occurrence of a song in the shared queue, with its own identity and requesting Remote. Two requests for the same song remain separate occurrences. **Playback time** in personal analytics means observed time playing a Remote's own requests, not proof that a person heard the audio.

The words **must**, **should**, and **may** identify obligations, recommendations, and options. Clauses marked **proposed default** are engineering choices that can be revised without changing a confirmed user requirement. Platform limitations do not silently waive requirements.

An implementation conforms to this baseline only when every applicable mandatory requirement has evidence in the acceptance matrix on the stated targets with at least two concurrent Remotes. Requested AutoMix and quality indicators remain experimental until their evidence exists. Documentation, mocks, and successful API lookups alone do not establish application conformance. The global SPEC.md remains a mandatory companion. No formal W3C QA Framework conformance claim is made.

## Native architecture

- **N01:** Host must use Swift and SwiftUI, with AppKit for system integrations when needed. Remote must use Kotlin and Jetpack Compose with Material 3 Expressive. Core operation must not require an embedded browser, Node.js, Electron, Flutter, or an Android audio playback engine.
- **N02:** Host must own authoritative pairing, policy, queue revision, request attribution, and playback observations. Remotes render replicated state and submit commands. Individual Remotes must not independently advance the shared queue.
- **N03:** Use a persistent authenticated TLS connection with WebSocket messages for commands and pushed state. Bonjour/mDNS and Android NSD are the preferred discovery path; a QR/manual-address fallback may be provided. These are implementation recommendations, not a requirement to introduce a separate HTTP server runtime.
- **N04:** Playback control must stay on the LAN without a cloud relay. Apple Music streaming, uncached catalog data, initial language models, and GitHub updates may require internet access. These dependencies must not be described as fully offline operation.
- **N05:** Remote core operation must work without Google Play services. Vendor Android APK behavior, discovery, background restrictions, and installation must be verified on representative target devices. Platform-specific forks remain outside the initial scope.
- **N06:** Cadenza must be maintained as one Git monorepo. Cadenza Host belongs in `apps/host`, Cadenza Remote in `apps/remote`, and shared LAN protocol contracts and fixtures in `shared/protocol`. The Windows project root is `D:\Dev`; each application retains its native build tooling.

Android's native design library is [Compose Material 3](https://developer.android.com/jetpack/androidx/releases/compose-material3). Select compatible pinned versions at implementation time; Material 3 Expressive does not by itself imply an Android 16 installation minimum. Vendor installation guidance may vary by device and firmware. These documents do not replace testing on representative target devices.

## Search and playback

- **B01:** Remote must search for songs in the Apple Music catalog and the Host library through Host, show identifying metadata, and submit a selected result for immediate playback or queuing subject to request protection. Full-catalog searching and playback of a song absent from the library require an explicit no-fee native Music.app proof.
- **B02:** Provide play/pause, next/previous, seek, and Music.app volume controls, with the ownership checks below applied to every operation that interrupts or changes a protected request. Search, playback selection, and the shared queue must refer to the same song version and occurrence.
- **B03:** Treat Host sleep, a logged-out session, unavailable Music.app, missing Automation/Accessibility permission, and failed state reads as explicit unavailable or unconfirmed states. Preserve accepted requests and entered search text. Do not report playback success solely because an Apple Event returned without an error.

[Native Music.app search automation](https://github.com/epheterson/applemusic-mcp) is a no-fee candidate. Apple's older [iTunes Search API](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/) may assist metadata lookup, but its store results must not be represented as complete Apple Music catalog coverage.

## Pairing and authorization

- **P01:** Host must accept more than one paired Remote at the same time. Pairing another Remote must not disconnect or overwrite an existing pairing. Host must show paired devices and allow individual revocation.
- **P02:** Pairing must establish a distinct authenticated device identity, using an out-of-band QR or code comparison to establish trust. Discovery is not authentication. Pairing codes must expire and be rate limited. TLS trust must not use an accept-all certificate handler.
- **P03:** Host must derive the requesting identity from the authenticated session. A caller-supplied name, owner ID, or queue-entry ID must not grant another Remote's permissions. Device credentials belong in platform secure storage, not plain SQLite columns or logs.
- **P04:** Only Host's local settings UI may change cross-Remote permissions. Policy checks must occur on Host immediately before a mutation is committed or dispatched to Music.app. Revocation must invalidate live access and subsequent commands.

## Request protection

Host must expose **Allow Remotes to change others' requests**. The proposed default is **off**. This setting must persist across Host restarts.

| Action through Cadenza                                                           | Setting off              | Setting on |
| -------------------------------------------------------------------------------- | ------------------------ | ---------- |
| Add a song to the end of the queue                                               | Allowed                  | Allowed    |
| Cancel own pending request                                                       | Allowed                  | Allowed    |
| Rearrange adjacent own requests                                                  | Allowed                  | Allowed    |
| Move ahead of another Remote's request                                           | Denied                   | Allowed    |
| Move or remove another Remote's pending request                                  | Denied                   | Allowed    |
| Skip another Remote's currently playing request                                  | Denied                   | Allowed    |
| Seek, stop, restart, replace, or jump away from another Remote's current request | Denied                   | Allowed    |
| Pause or resume the current playback                                             | Shared, proposed default | Shared     |
| Change Host policy or device permissions                                         | Host only                | Host only  |

- **P05:** Protecting the currently playing request is a confirmed requirement. Alternative commands such as seek-to-end, play-now, previous-track, or queue replacement must not bypass the skip restriction. Host's local controls always retain authority.
- **P06:** Request ownership must remain immutable when another Remote edits an allowed request. Keep the editor separate from the requester. Unrecognized items started directly through Music must be labeled as Host-originated and must not be attributed to a Remote by guessing.
- **P07:** Permission rejection must preserve the queue and immediately explain the blocked action in an accessible dialog. The permission must be enforced even if a modified client bypasses the UI.

The adjacent-own-request rule and shared pause/resume behavior are proposed defaults. They preserve the confirmed protection against skipping another Remote's request while avoiding queue jumping when cross-Remote edits are disabled.

## Shared queue and estimates

- **Q01:** There must be one shared ordered queue. Every row must show song, artist, requesting Remote, duration when known, and estimated wait. All Remotes must show the same committed revision. The initial insertion policy is FIFO by Host acceptance order; round-robin scheduling is outside scope.
- **Q02:** Each occurrence must have a stable request ID distinct from the catalog song ID. Commands must carry unique command IDs and expected queue revisions. Host must prevent duplicate enqueue operations on retries and reject stale edits without silently overwriting newer changes.
- **Q03:** A successful queue change must be reconciled with Music.app's actual native queue, persisted, and broadcast. A change must not be reported as applied while only an internal plan has changed. Native queue control is a prerequisite for preserving Music.app's AutoMix behavior.
- **Q04:** Each row's wait estimate must include the current song's remaining duration and all preceding requests. **Total remaining** must include the current remainder and all pending requests. Recompute after queue edits, track changes, seeks, and changed duration information.
- **Q05:** Estimates must be marked approximate when transition overlap is unknown. Subtract AutoMix overlap only when it can actually be observed. While paused, show paused status; unknown durations or live streams must produce an unknown or explicitly partial estimate. Unbounded future AutoPlay recommendations are excluded from the finite requested queue.
- **Q06:** Direct changes in Music.app must cause reconciliation and a new snapshot. If ownership or ordering cannot be matched safely, mark the affected state unresolved and prevent dependent edits until reconciled. Do not silently substitute a companion-managed playlist for native queue synchronization.

For example, with 2 minutes remaining now, a 3-minute request from A, and then a 4-minute request from B, B's estimated wait is 5 minutes and total remaining is 9 minutes before any known overlap.

## Personal analytics on each Remote

- **A01:** Each Remote must store per-song play counts and total playback duration in its own SQLite database. The proposed attribution rule credits the Remote that requested the song. Merely viewing lyrics for B's request does not increment A's personal play count.
- **A02:** A play is counted once for a distinct request playback occurrence after playback is confirmed to have started and progressed. A replay is another occurrence. A queued, rejected, expired, or canceled-before-play request must not count as a play.
- **A03:** Playback duration must use observed elapsed playing time and exclude pauses, unplayed requests, and time skipped by seeking. Do not equate a song's full duration or a jump in media position with time played. If native overlap telemetry is absent, count the authoritative foreground song and do not claim exact accounting for both AutoMix decks.
- **A04:** Host must deliver ordered, idempotent playback-credit events to the relevant Remote. Persist acknowledgments transactionally with aggregates so reconnection or an app restart cannot count events twice. Retain unacknowledged delivery data on Host until received; compact acknowledged data automatically. This delivery state is not a Host analytics dashboard.
- **A05:** Disconnected Remotes must reconcile outstanding credits on reconnect. If observations are missing, report the gap instead of inventing listening duration. Cache cleanup and normal updates must not erase personal aggregates or pairing identity. A Remote's private analytics must not be broadcast to other Remotes or uploaded to telemetry services.

The requester-attribution rule is an explicit proposed default; it measures request playback rather than room attendance or which person is physically listening.

## Synchronized sing along and English translations

- **L01:** Host must distribute one identified lyric document, English translation revision, active song occurrence, and authoritative playback timeline to all participating Remotes. Android must render and animate lyrics locally; the LAN must not carry a screenshot stream or animation frames.
- **L02:** First attempt read-only access to Music.app's own cached TTML. A [concrete cache reader](https://github.com/Yudaotor/lyrimuse/blob/35792d674f3dce7f55e5a00baba4fca6bf8a6715/lyrimuse-engine/applemusiclocal.go) reads `~/Library/Caches/com.apple.Music/fsCachedData/` and reports that Music's lyrics pane must be open. This is an undocumented implementation candidate, not a verified macOS 27 contract. Accessibility extraction is a secondary experiment. Validate cached documents without resolving external XML entities or following embedded URLs. Do not silently fetch another provider's lyrics.
- **L03:** Use Apple-supplied English translation when present. The proposed fallback is one translation on Host using Apple's native Translation framework, then distribution of that exact result to every Remote. Preserve stable lyric-line IDs and distinguish supplied text from machine translation. Unsupported languages must remain explicit; no paid translation service is required.
- **L04:** Models may be downloaded once with the OS's required interaction. Apple's [TranslationSession](<https://developer.apple.com/documentation/translation/translationsession/init(installedsource:target:)>) can use already installed languages outside a SwiftUI translation task; missing languages need the documented preparation flow. This makes Host translation a candidate for avoiding translation models and Google services on the tablet, subject to a no-fee runtime check.
- **L05:** Synchronization must handle pause, resume, seek, track changes, repeated song IDs, reconnect, and joining midway. Measure clock offset and round-trip uncertainty using monotonic clocks. Never apply a lyric update for the previous playback occurrence. Mark stale synchronization when the Host is unreachable.
- **L06:** The proposed timing acceptance target is at most 100 ms difference between Remotes for 95% of measured lyric-line transitions, no inter-Remote difference above 250 ms, and no Remote more than 250 ms from the Host playback timeline in the declared healthy-LAN test. Measure this independently from the 1-second command deadline; equally late displays do not establish synchronization with Music.app. Do not claim word-level highlighting when only line timings are available.

The same UI means matching song, lyrics, translation, and playback state. Layout may adapt to orientation, window size, text scaling, and reduced-motion preferences. It does not require identical pixel geometry on differently sized displays.

## AutoMix and current quality indicators

- **M01:** AutoMix must continue to run inside Music.app. The requested incoming-song and mixing indicator may be enabled only after the actual incoming item and transition state can be observed. Do not animate a guessed transition based on the end of the progress bar.
- **M02:** Read current Lossless, Hi-Res Lossless, and Dolby Atmos status from a validated playback-state source, with Music's playback badge as the first inspection candidate. An album's available formats, configured preference, or library bitrate are not proof of current playback quality. Display unknown when state cannot be established.
- **M03:** These indicators are conditional platform experiments. A release must disclose an unsupported feature rather than show invented state. Neither indicator may delay ordinary queue or transport controls.

Apple documents [AutoMix on Apple silicon](https://support.apple.com/en-au/105067) and currently excludes Hi-Res Lossless from AutoMix/Crossfade. Its [Lossless guide](https://support.apple.com/guide/music/play-lossless-audio-mus90b573cbb/mac) and [Atmos guide](https://support.apple.com/guide/music/play-spatial-audio-mus877f146ac/mac) distinguish catalog availability from the badge displayed during playback. macOS 27 extraction remains a target-device check.

## Realtime behavior and deadlines

The user's requested upper bound is **1,000 ms per request**. LAN transport alone does not bound Music.app execution, OS scheduling, Wi-Fi retransmissions, system sleep, or internet-dependent work. Cadenza must not claim a universal guarantee that successful playback or downloads finish within one second.

- **R01:** The proposed operational contract is visible pending feedback immediately, with confirmed success, explicit rejection, deadline failure, or an explicitly unconfirmed outcome by 1,000 ms after a control action. A quick acknowledgment is not successful completion. This interpretation preserves a firm feedback deadline; it does not establish the stronger successful-execution guarantee.
- **R02:** Commands must have a bounded lifetime. Expire commands waiting for dispatch; do not replay stale mutations after reconnection. Retrying an uncertain enqueue must use the same command ID and resolve the original outcome rather than create a second request.
- **R03:** A command already handed to Music.app may be impossible to cancel. If its outcome is not known by the deadline, mark it unconfirmed, read back state, and reconcile any later effect. Do not claim that the third-party operation was canceled or show a false success.
- **R04:** External searches, lyric availability, translation preparation, and update downloads must expose a responsive operation state within the deadline. Long-running work must have visible progress/cancellation where applicable and must not block local controls. Treating these as background jobs is part of the proposed interpretation, not evidence that their full duration is below one second.
- **R05:** Persist and push committed queue/policy changes to connected foreground Remotes within one second in the declared healthy-LAN acceptance run. Report latency from the initiating input to confirmed UI state, including failures and unconfirmed outcomes. Publish sample count, median, p95, p99, maximum, and deadline-miss count; do not hide missed requests from the measurements.

The successful-control target remains below one second. A deployment cannot be called conformant to an absolute all-conditions successful-execution limit on the basis of this response-deadline design. This distinction must be settled before implementing a stronger performance promise.

## Lean operation and size

- **S01:** Prefer OS frameworks and small maintained libraries. Host must not bundle a second media player or stream audio to Remotes. Remote must not include a web runtime or translation language packs by default. Keep the initial Host build arm64; broader architectures are outside the initial scope.
- **S02:** Use pushed state and local interpolation for progress and lyrics. Adapt state observation to active UI needs, batch SQLite writes, avoid persistent polling while disconnected, and stop lyric animations when hidden. No database write or network message is required for every animation frame.
- **S03:** Measure compressed release size, installed size, idle CPU, memory, active sing-along CPU, and network traffic on the targets. Record a numeric footprint budget after the native feasibility slice and before feature implementation. Every later dependency or unexplained regression must be assessed against that baseline. These measurements have not been made; no smallest-possible-size claim is warranted yet.

## SQLite and automatic maintenance

- **D01:** Host must use SQLite for pairing metadata, policy, attributed queue state, command receipts, and pending credit delivery. Each Remote must use SQLite for its pairing metadata, replicated-state cache, event acknowledgments, and personal aggregates. The implementation uses a small Swift SQLite layer on Host and Android's SQLiteOpenHelper on Remote to keep dependencies small; migrations and behavior must be verified on both engines.
- **D02:** Use transactional versioned migrations with schema checks and explicit recovery behavior. Before a potentially destructive migration, create a consistent backup through a supported SQLite backup mechanism. A migration failure must preserve the previous data and prevent dependent writes. Do not use destructive database recreation as migration fallback.
- **D03:** Use short transactions, serialized writes, foreign keys, prepared statements, and suitable indexes. WAL and checkpointing are recommendations where supported. Do not copy only the main database file while WAL writes are active; use the [SQLite backup API](https://www.sqlite.org/backup.html) or an equivalent consistent snapshot.
- **D04:** Automatically expire command receipts only after their replay-safety window, compact acknowledged delivery records, bound artwork/lyric caches, and remove obsolete update downloads. Keep credentials, aggregate analytics, and live requests outside cache eviction. Apply storage bounds with an explicit recoverable state rather than silently dropping unacknowledged analytics credits.
- **D05:** Run opportunistic optimization and checkpoints when idle. Incremental space reclamation may be configured for a compatible database; repeated full VACUUM during playback is inappropriate. [SQLite's optimize guidance](https://www.sqlite.org/pragma.html#pragma_optimize) and [WAL behavior](https://www.sqlite.org/wal.html) govern the chosen implementation. Maintenance must not block the control deadline, delete user history, or report corruption as repaired without verification.
- **D06:** Protect databases and backups using app-private storage and platform data-protection facilities. Any additional encryption needed for the actual exposure model must use maintained cryptography and keys in platform secure storage. Avoid persisting unnecessary plaintext lyric documents or analytics in diagnostic logs.

## GitHub Releases and self updates

- **U01:** GitHub Releases must be the source of released Host and Remote artifacts. Both apps must check for updates automatically and support updating themselves. The GitHub owner/name, release source, and signing keys must be configured before an installable baseline is produced; no GitHub remote or release is configured yet.
- **U02:** The proposed default is the stable channel, checks at startup when due and approximately daily using OS-scheduled work, and downloads on an unmetered connection. Automatically verify and stage updates, then install at a safe point when the platform allows; present any required OS confirmation. Background scheduling can be deferred by the OS. Checks and downloads must not disrupt playback controls. Native update UI must show version, progress, failure, and any required installation action.
- **U03:** Use HTTPS plus cryptographically signed release metadata/artifacts and pinned verification identity. Verify expected app identity, architecture, compatible protocol, version, hash, and signature before installation. A checksum hosted beside a malicious replacement is not sufficient authentication. Reject invalid packages and automatic downgrades; preserve the working installation on failure.
- **U04:** Android updates must retain the application ID, release signing identity or valid key-rotation lineage, and increasing version code. Use the supported PackageInstaller flow and required install-source authorization. [Android documents conditional unattended self-updates](<https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)>); always handle STATUS_PENDING_USER_ACTION. Silent installation is not guaranteed on Huawei firmware.
- **U05:** Host updates must work without paid Apple Developer membership and preserve its SQLite state and pairing secrets outside the application bundle. [Sparkle](https://sparkle-project.org/documentation/) is an established candidate with signed update archives, but its framework/signing requirements must pass a real ad-hoc-signed macOS 27 update test before selection. Do not weaken release security checks to make an updater load. A small native updater is an alternative only if necessary and validated.
- **U06:** Ad-hoc app updates can change the identity used by macOS privacy permissions; permission reauthorization must be handled honestly. Apple's [local-network privacy guidance](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) documents this limitation. Self-update support must not be advertised as permanently prompt-free installation.
- **U07:** Preserve queued requests, ownership, analytics, and acknowledged event positions through updates. Negotiate protocol compatibility so Remotes can update separately from Host. Stage installs safely; reconnect and resynchronize after an app restart. Music.app should continue playback while Host restarts, but uninterrupted native queue advancement must be verified.

Release keys must be backed up securely and excluded from source control and application bundles. Signing with developer-owned keys does not require purchasing Apple Developer membership. Private signing material must never be distributed in GitHub Releases.

## Interface and accessibility

- **I01:** Remote must provide the shared queue, now-playing controls, synchronized sing along, and its local analytics in a tablet-adaptive Material 3 Expressive interface. Host must provide a native menu-bar presence and settings for pairings, cross-Remote policy, permissions, and updates. Do not add unrequested services, accounts, or cloud analytics.
- **I02:** Follow WCAG 2.2 AA requirements applicable to native interfaces and the stronger platform accessibility conventions. Verify semantics, TalkBack/VoiceOver, keyboard/focus, contrast, large text, orientation, reduced motion, and alternatives to dragging queue rows. Use no eyebrow labels or filler subtitles.
- **I03:** Acknowledge actions at their triggers immediately and prevent duplicate submissions. Blocking permissions/errors require accessible dialogs with focus entry/restoration; routine outcomes use stable, accessible native toast/snackbar or equivalent notification surfaces. Do not insert transient outcome messages into normal layout flow. Long lyric content and scrolled queue views must not hide action feedback.
- **I04:** Capture actual working Host and Remote screenshots and exercise real workflows at representative macOS, Android portrait/landscape, expanded, compact, and narrow widths when UI is implemented. Mockups must be labeled as proposals and cannot stand in for target-device verification.

## Protocol and compatibility

- **C01:** Handshake must identify Host instance, authenticated Remote, protocol major/minor versions, and supported capabilities. Use structured bounded messages with validated IDs, durations, and revisions. No endpoint may accept arbitrary shell commands, AppleScript, filesystem paths, or update URLs from Remotes.
- **C02:** Unknown optional fields may be ignored. Unknown commands must be rejected without side effects. Unknown permission/capability values must not grant access. An incompatible protocol major must show an actionable update state before mutation; minor-version extensions must remain backward compatible.
- **C03:** The initial modules are Host control/pairing, shared queue, Remote analytics/Favorites, sing along, and self updates. AutoMix and quality observations are conditional capabilities. Major 1, minor 1 adds capability-negotiated Play next, editable names and idle heartbeats. The initial hello/pair shape remains compatible with older Host implementations. No general plugin/extension system is in scope.

## Remaining implementation decisions

- Confirm the proposed deadline interpretation, requester-attributed analytics, adjacent-own-request movement, and shared pause/resume defaults before depending on them as stronger product promises.
- Choose numeric size/resource budgets from milestone 1 measurements and select pinned library/toolchain versions that meet the device requirements.
- Choose the GitHub repository and establish backed-up artifact/APK signing identities before release engineering.
- Resolve the actual Music.app native queue adapter, lyric cache permissions, installed translation language pairs, and updater implementation through the target-device experiments above.
